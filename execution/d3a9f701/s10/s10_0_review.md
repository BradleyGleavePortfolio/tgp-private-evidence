## Findings

1. **A — A self-described snapshot/page chain becomes “source completeness proven” without verifying the claimed source proof (doc L92-96, L116-126, L142-145, L162-170, L318-330).** The only specified server comparison is against *staged* identities. A client can submit a digest of exactly those rows, a non-null arbitrary `snapshot_ref_digest`, `terminal: end_of_list`, and `passes: 1`, even if an earlier source page or a whole historical range was missed. The page-chain alternative has no page cursor/next-token linkage or source terminal artifact; two identical digests of two incomplete enumerations also pass. Thus E5/E6 can turn page/success assertions plus staged equality into `known: true`, and S9 can emit `complete`. The trust disclaimer and production Q2 acknowledge source honesty but do not change what E6 claims to prove. **Minimum textual fix:** distinguish an unverified observer assertion from a verified source completeness basis; specify a verifiable snapshot/cursor and terminal binding covering the full scope, or a chain of per-page cursor links/terminal evidence across both passes, and the trusted verifier for those artifacts. If this cannot be specified without deciding Q2, make such evidence `known: false` for a customer-visible Complete pending Q2; synthetic-only assertions may still be tested without asserting product completeness. Add the negative cases “arbitrary snapshot digest,” “same incomplete page chain twice,” and “missing/mutated page link.” See S9's requirement that visited-page success is not a basis ([S9 decision L186-225](worktrees/1910a060-s9b/docs/decisions/2026-09-25-s9-reconciliation.md)) and the current consumer of `known` ([coverage.ts L29-50](worktrees/1910a060-s9b/src/scout/reconciliation/coverage.ts)).

2. **A — The enumerated account scope is only checked for internal consistency, not against the run's intended source scope (doc L110-115, L142-145, L159-164).** All evidence can agree on one digest of an arbitrarily narrowed source account/workspace. No independently recorded expected scope, credential/account binding, or semantics for multi-workspace accounts is specified. A perfectly accurate enumeration of the wrong/narrow account can therefore be labelled complete. Moreover E4 demands *one* digest across all platforms, even when distinct platforms naturally have different account scopes. **Minimum textual fix:** bind each `(run, platform)` to an authoritative expected source account/workspace scope established before observation, compare the evidence digest to that binding, and explicitly define exhaustiveness across all authorized accounts; absent independent binding means `known: false`. Require agreement within a platform's evidence, not across unrelated platforms. If source-account binding is part of owner-reserved G3-AUTH/Q2, defer production Complete rather than assuming the binding.

3. **A — The staged identity digest can omit rows S9 treats as mapped (doc L133-138, L169-176).** The specified server computation uses `resolveStagedFamily`, which only calls `mapper.resolveStep`; S9-B `facts.service.ts` L484-492 additionally maps a token equal to a family in the spec even when that token is not in `steps` ([S9-B facts collector](worktrees/1910a060-s9b/src/scout/reconciliation/facts.service.ts), [mapper resolver](worktrees/d3a9-s10-read/src/scout/reconstruct/source-mapper-registry.ts)). An observed zero/count/digest could pass for the evaluator's empty partition while S9's native facts include an identity. This breaks the claim that E7 proves coverage of S9's staged set. **Minimum textual fix:** define one shared staged `(platform, family, source_id)` classification exactly matching S9-B's accepted canonical-token fallback (and S9-C as landed), or fail closed on any classification disagreement; assert a test where a canonical family token is declared but absent from `steps`.

4. **B — “DELETE happens only through the cascade” is not implemented by an UPDATE-blocking trigger (doc L200-209).** A direct service-role DELETE remains possible, and `ON DELETE CASCADE` defines actual deletion behavior while Q3 says erasure semantics remain undecided. The current L8 contract says hard deletion of the intent is restricted by the run and live account deletion tombstones instead ([S7-L L257-263](worktrees/d3a9-s10-read/docs/decisions/2026-09-24-s7l-run-lifecycle.md)). **Minimum textual fix:** say explicitly that cascade is *only* referential cleanup if the parent run is deleted under separately authorized L8 policy, and not a retention authorization; if “only via cascade” is an invariant, add a DELETE-blocking guard/privilege policy and a tested authorized parent-deletion mechanism. State that current tombstoning leaves both rows in place pending Q3. Do not silently choose a retention interval.

5. **B — CORE DIFF = 0 gate does not see untracked/dirty working-tree edits, and its allowed set is broader than the promised three artifacts (doc L238-256, L362-363).** `git diff B..HEAD` compares committed trees only; a dirty modified core path or untracked `src` file can be present when the gate reports success. `test/scout/s10/**` is unrestricted, so the phrase “D2 adds the three artifacts only” is not literally enforced unless tests/fixtures are separately enumerated. **Minimum textual fix:** pin B's full immutable hash after D1 lands, require `HEAD` to be a descendant and a completely clean index/worktree including untracked files (or explicitly compare all file bytes in the build input), and make the allowed delta precisely the three source files plus explicitly named synthetic tests/fixtures. Require the three artifacts to be present and diff only against B; use a bytewise check for every non-allowed core path. Treat a missing/failed `rg` invocation as a gate failure, while zero matches is success. Add a dirty-core-file negative control.

6. **B — The evaluator's “every contributing platform” is underdefined for unobserved platforms (doc L149-154, L174-178, L328-332).** S9 derives declarations from *staged* platforms and treats zero staged rows as undeterminable ([S9 types L228-235](worktrees/1910a060-s9b/src/scout/reconciliation/types.ts), [coverage.ts L57-81](worktrees/1910a060-s9b/src/scout/reconciliation/coverage.ts)); the doc alternately says “staged or declared platform,” without defining a run-level platform declaration independent of staging. In a multi-source run, a wholly omitted source can disappear from the required-family test. **Minimum textual fix:** define the authorized run-level platform set and require evidence for each of its declared families, or state S10 covers only staged platforms and cannot pronounce a multi-platform run complete without authoritative platform-set evidence. Preserve the existing zero-staged-run non-vacuity rule.

7. **B — The status projection contract is not mapped to S10-C's actual code change (doc L214-219, L294, L354-355).** `projectFamilies` initializes `observed_unique: null`; its `projectToken` returns no `observed_unique` field ([S9-C draft L731-805](worktrees/d3a9-s9c-r2/src/scout/lifecycle/lifecycle.service.ts)). The text requires settled counts to fill `families[].observed_unique` but the S10-C owned-path cell only describes a `'settled'` type-literal change in `types.ts` and settle/read work in lifecycle. **Minimum textual fix:** explicitly assign S10-C the `projectToken`/`projectFamilies` projection change; define multi-platform/family token merging and null behavior, and assert status counts agree with the stored report for one and multiple holders.

8. **C — Base/status wording is stale (doc L9-17).** The review's supplied current integration baseline is `5407efae` with S9-B landed; `771db62a` remains a valid read tree for the cited old paths, but “S9-B ... not landed” no longer describes the current branch. Refresh the status, maintain the explicit historical citation baseline, and recheck citations against the intended landing base.

9. **C — One source citation is mislocated (doc L23-24).** `S9B:src/scout/reconciliation/facts.service.ts` L478 is present in the S9-B worktree; the unprefixed `src/scout/reconciliation/types.ts` L207-220 is absent at the cited 771db62a tree. The text should prefix the S9-A/S9-B file citations with their actual landed/candidate base or update the declared base.

### New defects in changed text

1. **B-1 — Impossible negative proof expectations (L358-363).** R24 says “the same incomplete enumeration submitted twice” yields `known: false`, but a valid source signature over a statement claiming a full scope with matching identity digest/count, end marker and time passes E1–E6 regardless of a second identical submission. The evaluator cannot independently know the source lied; the contract explicitly trusts a source-held key (L83-88, L153-155). Likewise it cannot determine that a private key is “extension-held” merely from the signed bytes and public key; custody must be an external manifest approval fact. The deferred page-chain negative also cannot be tested as a missing/mutated *page link* in a schema that has no page-chain kind. **Minimum textual fix:** rewrite R24 as mechanically testable cases: unsigned/unknown-key signature; altered signed bytes; wrong challenge/scope/window; no manifest-approved source trust anchor; any unsupported page-chain payload rejected for unknown kind. State that a compromised/lying source is outside evaluator proof and that key custody/approval is a Q1/Q2 governance prerequisite, not a runtime oracle. Do not claim repeat enumeration alone detects a false source-signed assertion.

2. **B-2 — The claimed “FK action only” deletion guard is not identified by its proposed condition (L228-234, L384-387).** `pg_trigger_depth()>1` is a nesting-depth test, not evidence of *which* parent action caused a DELETE. The text promises the child can be deleted only by its FK cascade but gives the UPDATE/DELETE trigger a broader exemption. **Minimum textual fix:** either weaken the invariant to the actual permission/trigger guarantees and explicitly reserve privileged nested-trigger deletes to database governance, or specify a narrowly verified cascade-only mechanism and test a deliberately nested non-FK child DELETE negative control as well as the parent-cascade positive control. Keep the L8 policy boundary unchanged.

3. **B-3 — Declaration's one-shot set and challenge have no complete storage/idempotency contract (L99-108, L217-219, L252-265, L377-389).** The table holds one row per `(platform, scope)` with a `challenge` copied into each row, while the route returns *one* per-run challenge and the set is called immutable. No rule states that one atomic POST inserts the whole nonempty set, all rows carry the same random challenge, a replay returns that original challenge, or additional distinct rows are refused before staging. A partial/empty/mutated declaration could alter what “every declared platform and scope” means at settle. **Minimum textual fix:** require one atomic, nonempty declaration transaction under the run lock; unique platforms and nonempty unique scope arrays; one generated challenge duplicated consistently into all rows (or stored once under a run-level parent key); exact replay returns the original challenge, any changed or appended set returns `declaration_conflict` even before ingest; no state of “declared” arises from an empty list. Add tests for these cases and transaction rollback.

4. **B-4 — Source statement parsing and signature bytes are underspecified for the new signed artifact (L123-152, L179-184, L351-363).** “Canonical JSON bytes, signed by the source” and “signature over `statement_b64`” could mean signature over decoded bytes or base64 text. The statement includes a raw, unbounded `snapshot_id: string` even though L150-152 claims no free text/raw source identifiers; there is no explicit strict-key, duplicate-key, or length/encoding rule for the decoded statement. This can mislead both verifier interoperability and privacy/size proofs. **Minimum textual fix:** define strict canonical JSON serialization and base64 decoding; verify Ed25519 over the *decoded canonical statement bytes*, reject noncanonical/extra/duplicate fields, constrain the snapshot reference to a bounded non-PII digest or opaque safe token, and bound decoded statement, key and signature lengths. Make R21 cover these cases.

The new `OBSERVATION_CONFLICT_CODES` are separate from, rather than a mutation of, S9's append-only `RUN_REASON_CODES`; they cover declaration/observation conflicts without adding a terminal reason (L262-265, L338-342). The three-table FK/RLS/down/settle-time design remains otherwise coherent on paper, subject to B-2/B-3. No new A defect was established in the changed text, but the B defects make the contract and its proposed proof insufficient for GO.
