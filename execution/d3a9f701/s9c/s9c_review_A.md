## Blocking findings

1. **A — Settle-time facts do not have the required common snapshot.** `onTransferSettled` calls `this.prisma.$transaction(async (tx) => ...)` without an isolation option at `src/scout/lifecycle/lifecycle.service.ts:408-422`, whereas `readReport` explicitly requests `RepeatableRead` at `:661-670`. Addendum C-9 requires the **caller** to supply `REPEATABLE READ` for staging, ledger, provenance and native reads, explicitly including the S8-G settle transaction (`docs/decisions/2026-09-25-s9-reconciliation.md:570-575`). The facts collector first reads claim/staging/ledger, subsequently provenance, and then native rows (`src/scout/reconciliation/facts.service.ts:245-250,291-298,314-362`); under the default isolation, a concurrent native mutation or a later intent's provenance update can give a mixed-time classification. **Harm:** the persisted reason and native-verification account can represent no single database state (although v1's absent coverage still prevents `complete`). **Blocks:** C-9 snapshot guarantee and a trustworthy settle-time R09 verdict. **Minimum fix:** set `isolationLevel: Prisma.TransactionIsolationLevel.RepeatableRead` on the settle-tail transaction and add a test pinning that option plus a concurrent-change proof if claiming actual snapshot behavior. Handle any resulting serialization retry deliberately rather than silently weakening the guarantee.

2. **A — C-6 qualifier check is syntax-only, not domain validation.** `NATIVE_NAME_QUALIFIER = /^[a-z_.A-Z]+$/` and `admitReasonCode` accept any alphabetic qualifier/code with the right number of colon segments, including `unresolved:missing_required_field:Jane` and arbitrary bare words (`src/scout/lifecycle/lifecycle.service.ts:110-117,784-815`). The S9-A parser checks catalogue *code and qualifier shape*, but its own qualifier regex permits arbitrary alphanumeric strings (`src/scout/reconciliation/reconcile.ts:53-86`); the native writer similarly enforces a regex, not membership in the spec's fields (`src/scout/reconstruct/native/native-contract.ts:59-83`). Addendum C-6 expressly requires validation **against the spec's family, field and model names before a DTO**, not merely this regex (`docs/decisions/2026-09-25-s9-reconciliation.md:560-566`). The new test rejects an email-form qualifier but never a syntactically valid, out-of-domain name (`test/scout/lifecycle/lifecycle.service.spec.ts:940-976`). **Harm:** a malformed/persisted reason containing a person's single-word name can appear in the customer-facing `families[].reasons` histogram; the closed-catalogue/PII promise is not actually established. **Blocks:** C-6 and the R14-facing safety guarantee of this projection. **Minimum fix:** admit each qualified code's qualifier only from the corresponding registered spec/native field/model/family domain (and constrain bare codes to the catalogue), folding anything else into `unresolved:reason_unrecognised`; test `:Jane` and valid native names. Do not treat the current regex as an allow-list.

3. **B — C-9 catalogue equality is a documented but unapproved deviation.** C-9 says S9-C adds a spec asserting S9-A's §3.7 catalogue **equals** S8-C's runtime `UNRESOLVED_CODE` (`docs/decisions/2026-09-25-s9-reconciliation.md:570-575`). The new spec instead asserts 12 runtime codes are a subset of 15 S9-A codes and pins the three extras `date_zone_unknown`, `no_native_destination`, `unit_unknown` (`test/scout/reconciliation/catalogue-parity.spec.ts:7-19,33-61`); the actual lists are at `src/scout/reconstruct/native/native-contract.ts:42-56` and `src/scout/reconciliation/types.ts:354-375`. This is a reasonable compatibility *rationale*, but **not** an acceptable literal reading of “equals.” **Harm:** a green test can be presented as proof of a contract property it does not assert; subsequent catalogue drift can be handled under the wrong policy. **Blocks:** declaring Addendum C-9 satisfied. **Minimum fix:** obtain a recorded owner-approved amendment specifying subset plus exact surplus, or coordinate the catalogue ownership change needed for actual equality and assert equality. Do not silently widen S8-C or edit frozen S9-A as part of this narrow slice.

4. **B — The live R09/R10(C)/R11/R13/R15 proof is designed but not yet executed on this candidate.** `test/rls-g2-s9c.spec.ts:156-244,246-419,421-596` has non-vacuous fixture rows, actual service calls, one-terminal-write and CAS-miss query-order assertions, a two-coach comparison, legacy key-set assertion, and report/read equality. Yet the candidate is dirty/uncommitted and both the harness and bootstrap demand a clean, attested non-base head (`test/utils/g2-s9c-pg-harness.ts:35-49`; `test/utils/g2-s9c-bootstrap.sh:40-50`); the supplied 14-suite dev-loop record does not establish that the separate `jest.rls.config.js` suite ran. **Harm:** a prospective proof may be mistaken for observed behavior; its database-specific assertions have not been validated on these bytes. **Blocks:** claiming live-PG acceptance, not the static code review. **Minimum fix:** after resolving findings and freezing a clean, attested candidate, bootstrap the isolated `g2_s9c_disposable` lane and run/retain the dedicated live suite with a run log bound to its head and manifest.
