# S10-C independent T4 source review A

**Verdict: NO-GO for acceptance/landing on the current nine-path draft.** The settle-write architecture is substantially aligned with D-S10-4, but the no-basis fallback changes the promised S9-C report semantics, the mandated live Complete case is not covered, and landed S9-C live assertions will fail unchanged. This review was read-only; I did not run tests, Prisma, PostgreSQL or the lock. The current worktree at `a2c74e90` has four modified production paths, two modified existing tests and three new specs, with no S10-C Prisma/migration or reason-code change (`git status --short` in `worktrees/d3a9-s10c`).

## Findings

1. **A — no-settled-basis fallback can produce a new coverage result instead of the specified S9-C recompute.** D-S10-4 says that without a basis row (including pre-S10 and fence-path terminals), the S9 recompute stays `'recomputed'` and byte-identical to S9-C (`docs/decisions/2026-09-26-s10-induction.md:265-272`). Yet `readReport` passes the terminal row's accepted start and epoch into the collector when the basis lookup returns null (`src/scout/lifecycle/lifecycle.service.ts:783-795`). The collector then reads declarations/current-epoch observations and calls the S10 evaluator rather than returning S9's `coverage: null` (`src/scout/reconciliation/facts.service.ts:608-618,628-654,877-926`). For a fenced server run that already has a valid declaration and signed observation, the report may now show a known count/basis and even no coverage condition despite the absence of a settled record; for older terminals, later evidence or backfilled S10 rows can change their report. The current unit test only compares a mocked collector returning preselected `MIXED` facts, so it cannot detect this (`test/scout/lifecycle/lifecycle.service.spec.ts:1469-1488`). **Harm:** a customer-visible report for a fence/pre-S10 terminal can contradict its historical no-basis truth and cease to be the promised byte-stable S9-C fallback. **Blocks:** D-S10-4 status/fallback acceptance. **Minimum fix:** on the no-basis branch, call the collector without a run binding (or explicitly with `null`) to retain S9's unknown coverage; add a test with valid declaration/observation and no settled row asserting `coverage_basis_unknown`, null `observed_unique`, and no S10 evidence read. If the owner intends recomputation using later S10 evidence, amend D-S10-4 first and explicitly prove the changed semantics.

2. **B — R33 live Complete half is unproved.** R33 requires a native-clean, fully declared/verified success claim to become `complete`, with one terminal write and one settled-basis row (`docs/decisions/2026-09-26-s10-induction.md:428-432`). The new live spec explicitly uses the frozen S10-B worker with no induction manifest and asserts the terminal is **not** complete (`test/rls-g2-s10c.spec.ts:14-20,97-126`); the builder's unit-tier synthetic case does exercise a known covering basis (`test/scout/lifecycle/lifecycle.service.spec.ts:1377-1419`). **Harm:** a passing 24-test S10-B suite or this structural PG case could be mistaken for a real-PG proof that the newly reachable Complete verdict and basis insert work together; database/transaction faults on that positive path remain untested. **Blocks:** R33 as a T4 live-PG acceptance claim, not the unit-level logic. **Minimum fix:** provide a controlled manifest/registry seam in the real worker (with corresponding binding) and a live positive Complete case, or obtain an explicit owner-approved acceptance amendment deferring the live verdict half while retaining its unit proof. Do not call the current structural case full R33.

3. **B — the landed S9-C live proof is guaranteed red against this change without an owned reconciliation of its assertions.** `test/rls-g2-s9c.spec.ts:289` asserts the terminal UPDATE is the final tail statement and `:297` expects `basis:'recomputed'`; its status case expects a REPEATABLE READ transaction and S9 read (`:442-448`). S10-C deliberately inserts an observation SELECT and basis INSERT after that UPDATE in the same transaction and returns the stored `'settled'` report without recompute (`src/scout/lifecycle/lifecycle.service.ts:462-468,542-575,783-786`). The builder identifies two of these conflicts but does not mention the `:297` basis assertion; none of the landed live spec is among the nine changed paths (`s10c_builder_summary.md`, “Landed specs this change is EXPECTED to break”). **Harm:** a full live regression run fails by design and can be misread as a product failure, or skipped to manufacture a green acceptance claim. **Blocks:** a clean, noncontradictory T4 proof and regression gate. **Minimum fix:** secure a narrow test-owner/scope grant and update the superseded S9-C assertions to preserve their enduring properties (one terminal UPDATE, same transaction, no status writes, unchanged token projection), while allowing the post-CAS basis record and settled status preference; account for `:297` as well as `:289,442-448`. Run the revised live suites on an attested candidate.

## Other requested checks

- **No false Complete / unknown handling (static):** the collector's default registry is built from on-disk manifests and its mapper partition (`src/scout/reconciliation/facts.service.ts:337-369`); staged digests use the same `resolveFamily` classifier as reconciliation, including declared zero-row families (`:264-317,658-673`). Missing/non-server/unaccepted run binding yields `coverage: null` without S10 reads (`:628-637`); evaluator failures return `known:false` rather than invented zero (`src/scout/induction/verify.ts:263-363,371-380`). S9's pre-existing predicate still enforces success claim and full family coverage; R23 uses the already-landed `coverage_basis_unknown` code, not a new enum (`test/scout/lifecycle/lifecycle.service.spec.ts:1401-1419`). The new live spec cannot validate a real positive Complete case (B-2).
- **Settle ordering and idempotence (static):** the locked server row supplies epoch/start, the arbiter receives the S9 verdict, and `writeSettledBasis` runs only after a successful `writeTerminal` CAS in the same repeatable-read transaction (`src/scout/lifecycle/lifecycle.service.ts:446-469,508-538,542-575`). The basis insert uses the coach/intent PK and same-epoch observation digests; a CAS miss skips it and an insertion error rolls back the transaction. Analytics occurs only after success (`:470-476`). The new unit and prospective PG specs assert order, a concurrent loser, one row, and injected insert rollback (`test/scout/lifecycle/lifecycle.service.spec.ts:1271-1358`; `test/rls-g2-s10c.spec.ts:97-235`). The direct `fence()` method still writes no basis; a fenced-but-open tail that itself wins the CAS records the report beside the fence verdict, which is not a second terminal writer.
- **Read preference, tenant and epoch:** a valid version-1 settled row is fetched by `(coach_id,intent_id)` and returned without a recompute; malformed/missing records fall back (`src/scout/lifecycle/lifecycle.service.ts:783-827`). Declaration reads carry coach/intent, observation reads carry coach/intent/**execution_epoch**, and the basis write rereads only that epoch (`src/scout/reconciliation/facts.service.ts:877-926`; `src/scout/lifecycle/lifecycle.service.ts:542-575`). The evaluator also checks row identity/epoch (`src/scout/induction/verify.ts:181-194`). Status does not reach the basis lookup for legacy/open/nonapplicable runs (`lifecycle.service.ts:762-785`), and the live spec checks another coach receives 404 without the basis query (`test/rls-g2-s10c.spec.ts:270-276`).
- **Projection, side effects and scope:** finding 7 is implemented by filling a token's `observed_unique` only for one mapped holder, one token, a settled report and a numeric non-null count; otherwise it retains the nullable base shape (`src/scout/lifecycle/lifecycle.service.ts:890-947`; `docs/decisions/2026-09-26-s10-induction.md:359-363`). The added source imports ObservationModule only, and adds no notification/drip/mail sender; the existing `ScoutModule` already imports NotificationsModule, so “none” should be read as **no new S10 side effect** (`src/scout/scout.module.ts:17-23,42-50`; `test/rls-g2-s10c.spec.ts:90-102,238-257`). The nine paths are within the S10-C row of D-S10-7; `reconcile.ts`, `coverage.ts`, `arbiter.ts`, `reason-codes.ts`, migration and Prisma schema are untouched by this S10-C diff (`docs/decisions/2026-09-26-s10-induction.md:351-356`; `git status --short`). The source-name-literal negative is represented by `test/scout/induction/s10c-wiring.spec.ts`; no new source-specific production branch was found.
