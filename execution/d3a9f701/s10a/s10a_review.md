## Findings

1. **B — R27's real grouping fallback is not proved (release proof blocker).** `test/scout/induction/verify.spec.ts:490-517` declares a local `steps` object and computes `steps[token] ?? token`. It never calls the actual `facts.service.ts:484-493` classifier or its grouped rows. Removing the canonical-family-token fallback from that production classifier would leave the R27 test green while staged identities could be omitted from E6 and an otherwise valid signed count/digest could incorrectly appear covering. **Blocked:** claiming the R27 acceptance case and E6 integration are proved by S10-A. **Minimum fix:** once S10-C exports the single production classifier/grouping as contracted, feed its actual grouping into the staged-digest test and retain the no-`steps` token plus a negative partition-disagreement assertion; until then mark R27 provisional rather than passed. **Unblocks:** a non-vacuous end-to-end grouping proof for the `complete` gate. The local assertion *is* non-vacuous for `verify.ts` digest consumption, but vacuous for the specifically named S9-B fallback.

2. **B — R25's “declared scope unproven” case is not isolated (proof gap).** `verify.spec.ts:414-425` supplies proof for **both** scopes, then expects unknown solely because `verify.ts:278-279` rejects *every* multiscope platform in v1. If the all-declared-units proof check were removed, that assertion would still pass. The one-scope undeclared-scope negative at `verify.spec.ts:428-431` and absent-evidence R26 at `:485-488` do cover related failures, but neither independently establishes the multi-unit “one missing proof” proposition. **Blocked:** representing that subcase as independently demonstrated by the R25 test. **Minimum fix:** explicitly test two scopes with one missing/invalid proof, while acknowledging that v1's blanket multiscope refusal makes the outcome non-discriminating; defer a discriminating all-units assertion to the first implementation with scope attribution, or narrow the claimed R25 proof to the v1 refusal. **Unblocks:** accurate acceptance accounting without a false claim of guard isolation.

3. **B — R23's terminal `partial/coverage_basis_unknown` is not asserted.** `verify.spec.ts:206-223` checks `known:true`, `covers_staged_identities:false` and `familyCoverage(...).completeness_basis === 'none'`; it does not invoke the arbiter to assert the named terminal outcome. The evaluator result itself is well tested. **Blocked:** claiming the full R23 arrow through terminal outcome on these tests alone. **Minimum fix:** add a composition assertion using the landed arbiter and otherwise complete reconciliation facts (or explicitly allocate the terminal check to S10-C), asserting `partial/coverage_basis_unknown`. **Unblocks:** proof of the advertised customer-visible status, rather than only the coverage projection.

4. **C — reduce S10-A size by moving route-envelope work to S10-B.** `parse.ts:250-300` (`ParsedObservationUpload`, `parseObservationUpload`) and `parse.spec.ts:236-261` implement/test the HTTP body envelope, `intent_id`, body cap and cardinality. These are S10-B route/DTO concerns; retaining `parseEvidence` and its parser tests still covers the S10-A cryptographic/grammar work. Move the 32-KiB acceptance check and accompanying route-body tests into S10-B, not delete the check: R21 explicitly requires that bound. This saves roughly 50 implementation lines plus approximately 26 test lines, not the entire ~1,100-line excess. Additional consolidation could use table-driven cases in `manifest-registry.spec.ts:97-251` and `verify.spec.ts:226-331`, preserving independent negative controls.

## Security and contract checks

- **E1–E6:** `verify.ts:110-125,141-235,242-343` checks declaration, unique parsed evidence, run/manifest/spec binding, approved-manifest-key signature and statement fields, date window, count/digest consistency and family-set agreement. Any exception in evaluation produces all canonical families `{known:false}` (`:351-361`); no untrusted error path visibly produces `known:true`. A failed or absent unit never becomes zero. Multiscope refusal is deliberately fail-closed. `verifyEd25519` checks the decoded statement bytes, not its base64 (`:217-222`).
- **Custody is necessarily external:** `verify.ts:217` accepts exactly keys in the loaded manifest; the fixture manifest names only the synthetic source public key. A signature made with the observer fixture key is rejected when it is not in that manifest (`verify.spec.ts:226-245`). Software cannot identify physical private-key custody from a public key: if governance incorrectly approves an observer-held key into `verifiers`, the evaluator **will** accept it. This is explicitly reserved by D-S10-1/Q1/Q2, not a newly discovered code bypass; no real verifier manifest is present. The temporary two-verifier positive parser test (`manifest-registry.spec.ts:236-245`) merely establishes grammar and should not be presented as custody approval.
- **Encoding:** `parse.ts:69-79,125-181,196-229` enforces standard padded base64 plus round-trip pad bits; fatal UTF-8, no BOM, ≤1,024-byte decoded statement, exact keys and byte-identical canonical reserialization exclude duplicates, order/spacing changes, noninteger number spellings, nonminimal Unicode escaping and malformed surrogate text. It validates 32-byte challenge, 64-byte signature, 32-byte public key (`:294-312,330-345`), digest grammar including `snapshot_ref_digest`, timestamp grammar/window and count bounds. The snapshot reference has no raw reference field or independently verifiable preimage requirement. This is not a claim that JSON objects uploaded as evidence must preserve original textual key order; the strict canonical requirement applies to signed statement bytes.
- **Digest:** `digest.ts:77-90` UTF-8-byte-sorts distinct IDs and hashes concatenated byte-length-prefixed records; separators within IDs cannot create ambiguous framing. It does not Unicode-normalize, correctly treating canonically equivalent but byte-distinct IDs as distinct; lone surrogates fail closed (`:12-16,80`). E6 separately binds digest *and* count (`verify.ts:304-310`), rejecting equal digest/unequal count, while a different digest remains known but uncovered.
- **Other A-tier tests:** R20, R21, R22, R24(a–k), R26 and the `verify.ts` portion of R28 have positive baselines and discriminating negative assertions in the named specs. R21's over-limit statement asserts the exact `too_large` rejection, so it would fail if its size guard were removed even though its whitespace payload would still be invalid JSON. R28's named-slug scan is finite, but the source files reviewed contain no source-specific dispatch.
- **Scope/hygiene:** Files read are confined to the S10-A-owned five source modules, five matching specs and `test/fixtures/scout/s10_pure/**`. No real manifest, real key, production source JSON or new dependency appears among them. No R75 banned literal was found by focused text search in those paths; this was not an execution of the policy checker. The builder's custody, missing-manifest, invalid-row and no-spec choices fail closed. Its other listed decisions (strict multiscope refusal, conservative timestamp interval, malformed-id rejection and partition disagreement) likewise do not contradict the contract.

**Disposition:** NO-GO for an unqualified “all A-tier acceptance proved” handoff until findings 1–3 are fixed or explicitly assigned as outstanding composition proofs. I did not identify a direct forged-signature or canonical-encoding bypass in the inspected S10-A code. This is source review only; the parent must still run its authorized validation separately.

## Delta re-review (fix rounds 3-4)

**Verdict: GO for the changed S10-A regions**, retaining the R23/R27 and route-enforcement handoff boundaries above. This was source inspection only; the parent reports a green devloop-3, but I did not rerun it.

- `verify.ts:264-285` indexes the first staged platform as `{kind:'facts', facts}` and every subsequent occurrence as `{kind:'conflict'}`; even a third occurrence stays conflicted. For a declared platform, that conflict makes `partitionAgrees` false and fails all its families; for an undeclared platform, `verify.ts:327-337` emits/fails canonical families. There is no conflict branch that substitutes an empty staged set or yields `known:true`.
- `verify.ts:300-330` rejects a grouped family missing from the staged digest map *before* the empty-set fallback. A `null` digest also fails. The empty digest/count zero is now used only when no staged entry exists or the family is absent from **both** the grouping and digest map; with a valid present staged entry, `sameSet(grouped_families, expectedFamilies)` means every declared family must be grouped, so a missing digest cannot masquerade as a known, covered zero. If the signed digest differs, `covers_staged_identities` remains false; equal digest with unequal count still fails.
- `verify.spec.ts:706-750` is discriminating. Duplicate-platform input tests the conflict branch against an otherwise proven baseline. The missing-map case pairs a valid empty-set signed statement with a `programs` grouping but no `programs` digest; without the new guard it would become `KNOWN(0, true)`, contrary to the asserted family-specific unknown. The duplicate-family case explicitly checks that the staged helper returns `null` for `clients` while the other family digests remain present and known. `digest.spec.ts:97-107` mutates a valid parsed spec's client display-name path and checks the digest changes, correcting the previously invalid fixture mutation.

**No new A/B finding.** S10-C still must populate staged digests from its real grouping, including empty-set entries for grouped families with zero rows, and retain the declared/undeclared partition fail-closed behavior in composition.
