## A/B findings (five required fields)

### B1 — Present-tense RLS guarantee is false; person-owned check-ins can be directly visible to the coach

- **CLASS:** B, privacy/security contract error.
- **CONCRETE HARM:** §2.2 says person-owned rows are unreadable to `anon`/`authenticated` because `user_id` is NULL and quotes an obsolete policy. The later effective migration replaces it with `check_in_coach_select`, whose predicate is `coach_id = app.current_user_id()` irrespective of `user_id` ([`20260607000000_rls_remaining_gaps/migration.sql` L351–390](../../../../../../worktrees/fa72-s8d/prisma/migrations/20260607000000_rls_remaining_gaps/migration.sql)); `CheckIn.coach_id` is nullable and independent of `user_id` ([`schema.prisma` L1102–1107](../../../../../../worktrees/fa72-s8d/prisma/schema.prisma)). Thus a person-owned check-in with populated `coach_id` is visible to that authenticated coach through direct DB access, contrary to §2.2's deny-by-construction assertion ([decision L114–126](../../../../../../worktrees/fa72-s8d/docs/decisions/2026-09-26-s8d-person-link.md)). The owner RLS policy also exists, so "unreadable to authenticated" has a deliberate owner exception. `ClientWorkoutAssignment` and child snapshot have distinct policies, not the asserted five-table uniform `user_id` predicate.
- **EXACT DECISION BLOCKED:** Accepting §2.2's fail-closed privacy model and approving S8-D3/S8-E person-owned write paths.
- **MINIMUM CLOSURE:** Inventory **effective** policies for all five parents and children, specify explicit `person_id IS NULL` guard for any direct client/coach access unless the owner decides otherwise, and test `anon`, unrelated authenticated principal, same coach, linked client, and owner against both owner states. State intended owner exception truthfully; protect cross-tenant `coach_id` on check-ins.
- **EXECUTION UNLOCKED:** Accurate RLS design and S8-D3 schema work; no production enablement.

### B2 — Proposal rows conflict with active-link constraint and have no secure lifecycle

- **CLASS:** B, integrity/authorization.
- **CONCRETE HARM:** §3.3 inserts a `PersonLink` with `coach_confirmed_at` but **no** `linked_at` for L5/L8, while §2.5 calls `PersonLink` the inserted link/audit record and defines the active partial uniques only by `unlinked_at IS NULL` ([decision L203–226, L356–370](../../../../../../worktrees/fa72-s8d/docs/decisions/2026-09-26-s8d-person-link.md)). An unconfirmed proposal therefore occupies the active Person/account slot; state, deadline, expiry, decline, revocation, and exclusion from the roster/claim precondition are undefined. Worse, `path = merge` bypasses the account unique index without a DB-enforced anchor, inviting multiple active merge-typed rows.
- **EXACT DECISION BLOCKED:** S8-D3 table/index design and S8-D6 two-sided fallback/merge.
- **MINIMUM CLOSURE:** Model pending proposals separately or add an explicit pending/active/declined/expired state, with active uniques applying only after `linked_at IS NOT NULL AND unlinked_at IS NULL`; define proposal expiry, revocation, authorization, transitions, and same-transaction activation. Constrain merge anchor's coach, account, active state, and Person distinctness; resolve OQ-1 before this index lands.
- **EXECUTION UNLOCKED:** Safe schema D3 and fallback D6.

### B3 — Fresh-invite requirement can be bypassed by the fallback after unlink

- **CLASS:** B, owner-decision fidelity/security.
- **CONCRETE HARM:** L7 requires **fresh invite + fresh client confirmation** for re-link after unlink ([binding owner decision L7](../OWNER_DECISION_S8D_2026-09-26.md)); the record repeats it in §2.8, but allows `Claimed → InvitePending` on unlink and then `InvitePending → Claimed` through a coach-approved match **without any invite row** ([decision L151–152, L310, L361–370](../../../../../../worktrees/fa72-s8d/docs/decisions/2026-09-26-s8d-person-link.md)). A previously unlinked client can be re-linked via L5 without the decided fresh invite.
- **EXACT DECISION BLOCKED:** Approval of L5/L8 transitions and D6, and the interpretation of L7 as implemented.
- **MINIMUM CLOSURE:** On a Person with any historical link, require a newly minted Person-bound invite and new challenge plus client confirmation for **every** re-link path; or get a new explicit Bradley decision changing L7. An in-app match proposal alone must not satisfy it.
- **EXECUTION UNLOCKED:** Owner-faithful L5/L8 implementation.

### B4 — S8-D1's create-only/replay contract and Deleted treatment must be decided before the handoff

- **CLASS:** B, native truth/identity contract.
- **CONCRETE HARM:** D1 turns `person` into a provenance-carrying native target; the existing upsert overwrites `display_name` on replay ([`families.ts` L83–101](../../../../../../worktrees/fa72-s8d/src/scout/reconstruct/families.ts)), while native writers use provenance to verify a target and preserve edits ([`native-writers.ts` L91–105](../../../../../../worktrees/fa72-s8d/src/scout/reconstruct/native/native-writers.ts)). OQ-11 leaves this unresolved although the existing S8-DOC's D-S8-4 create-only rule is binding. Also D1 proposes `Deleted → removed` in S9 facts but does not say whether a replay of a deleted external reference must refuse reactivation; `clientsFamily.persist` currently upserts regardless of `Person.state`, and `readPersons` currently does not inspect state ([`facts.service.ts` L1003–1014](../../../../../../worktrees/fa72-s8d/src/scout/reconciliation/facts.service.ts)). Simply making its typed result `already_present` risks reporting a terminal deleted Person as an accepted native outcome, and repeated writes can overwrite a later user/coach edit.
- **EXACT DECISION BLOCKED:** The D1 `complete` claim for person roster rows and D1 implementation grant.
- **MINIMUM CLOSURE:** Set OQ-11 to create-only (preserve existing display name on provenance replay); define replay verification of tenant/external ref and `Deleted` before emitting `already_present`, with a truthful `removed`/unresolved result and no silent resurrection. Add cases for edited names, deleted targets, historical NULL-kind ledgers, and repeated runs.
- **EXECUTION UNLOCKED:** Safe typed-person provenance D1 and honest reconciliation.

### B5 — Guaranteed unlink is not deployable in the planned incremental order

- **CLASS:** B, release/security boundary.
- **CONCRETE HARM:** D4b introduces a completed link and starts the 30-day clock; D5 alone supplies either party's unlink route and return-only-imported transaction ([decision L258–295, L372–379, L459–464](../../../../../../worktrees/fa72-s8d/docs/decisions/2026-09-26-s8d-person-link.md)). A partial deployment or enabling D4b before D5 denies Bradley's L7 recovery right while consuming time on a fixed deadline. The document says the Scout feature is dark by default but never specifies an atomic enablement gate across D4b+D5.
- **EXACT DECISION BLOCKED:** Exposing claim/link in any environment with real client data.
- **MINIMUM CLOSURE:** Explicitly forbid claim enablement until D5 client/coach undo and notification paths have landed and been verified; ideally land D4b+D5 as one releasable gate. Document failure/retry path when a link's post-commit notification cannot be delivered.
- **EXECUTION UNLOCKED:** Safe staged implementation without premature live claim.
