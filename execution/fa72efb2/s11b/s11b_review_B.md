## Answers to the grant

1. **Terminal truth and fencing (J13, J15 b, J16).** The replayed completion first tries the original gated claim transaction; only a `P2002` from that transaction enters the new branch. A *second*, short transaction takes the writer gate as its first query, then checks open/unfenced/reconciling/completion-row pending state, and passes the gate-returned database epoch to the existing settle pass (`src/scout/scout.service.ts:381–417,429–443`; `src/scout/lifecycle/lifecycle.service.ts:638–666`). A fence between the refused insert and this gate makes the gate return null; a fence **after** that transaction commits but before or during the pass makes a per-row gate fail or raises the epoch, and a fence before the tail lock causes the terminal/epoch test to return null. If settle instead holds the tail run-row lock first, the fence waits for its transaction and cannot retroactively revoke that already-won settle (`lifecycle.service.ts:382–403,434–465,506–513,527–534,638–647`). The tail is a repeatable-read transaction with bounded serialization retries, each retry beginning with the lock/epoch/terminal check; terminal CAS and basis insert share that transaction, and only a winning outcome emits the settle event (`lifecycle.service.ts:443–473,477–503,520–570`). Two workers may both complete the pass, but their tail transactions serialize or one retries and observes terminal: **one successful terminal/basis pair**, not two. Neither the new branch nor the pending read chooses a verdict: the tail reads the stored claim and durable facts, calls reconciliation and the existing arbiter; a missing reconciliation cannot become `complete` in that arbiter (`lifecycle.service.ts:448–465,583–609`; `src/scout/lifecycle/arbiter.ts:4–9,65–87`). No concrete counter-interleaving yielding a different terminal or settling a revoked epoch was found.

2. **Replay and pure ack (J12 tail, J14, J15 a/c).** On P2002, the refused claim transaction rolls back and the new branch has no completion update/upsert, no notification and no completed analytics event; the status in the replay body is never passed to `onTransferSettled` (`scout.service.ts:383–425`). A terminal/fenced run fails the *first* gate and returns ack after classification without reaching the insert or re-drive; a never-started run retains the 409 path (`scout.service.ts:383–405`; `lifecycle.service.ts:638–647`). On a still-open but non-pending run, the second gate and pending read return an ack without a settle (`scout.service.ts:409–414,436–443`; `lifecycle.service.ts:658–666`). “Pure ack” means **no new claim, phase/terminal/basis, push or completed event**, not literally zero SQL writes in the unusual open/non-pending case: the pre-existing gate updates `last_observed_at` (and discovering→transferring, if applicable) before pending is read (`lifecycle.service.ts:638–646`). J14 explicitly sends a `success` retry after a stored `partial`, checks the completion row remains `partial`, and compares the entire resulting shape to an uninterrupted `partial` reference (`test/scout/s11/settle-redrive.pg.spec.ts:375–396`).

3. **Unknown/zero and invented behavior.** The addition is an eligibility predicate plus a call into the unchanged pass/arbiter, not a new projection or count converter (`scout.service.ts:409–443`; `lifecycle.service.ts:658–666`). Status still projects the run row and reads the actual claim and report; the snapshot flush cannot decide the terminal (`scout.service.ts:281–303,458–506`). The existing arbiter produces `complete` only via reconciliation, otherwise `partial` when no verdict exists (`arbiter.ts:65–87`); the terminal+basis record comes from the same transaction (`lifecycle.service.ts:448–465,547–570`). Thus no S11-B path turns unknown into zero/complete, or fabricates a server terminal.

4. **Discriminating tests and R36.** The 11 unit cases distinguish the wrong epoch (first gate 7, second gate 9, body 42), reversed or split eligibility sequencing, a missing pending test, P2002 broadened to other errors, extra push/event, changed first-claim flow, and non-tenant-scoped/writeful pending SQL (`test/scout/lifecycle/s11b-settle-redrive.spec.ts:110–160,163–255,278–307`). Their doubles do not establish live locking or terminal facts; the eight real-PG cases do: a killed worker's committed claim and partial pass, reference-shape equality, further retry no-op, stored-claim mismatch replay, fenced/terminal/never-started no-op, and tenant isolation (`test/scout/s11/settle-redrive.pg.spec.ts:158–213,238–316,375–498`).

   **J13 is not a vacuous one-worker race.** The worker's `before-lock` barrier fires in `$queryRaw` *before* a `FOR NO KEY UPDATE` query, and its gate uses UPDATE rather than that SQL phrase (`test/utils/g2-s11-worker.cjs:191–194,201–245`; `lifecycle.service.ts:638–646`). The replay's qualifying read itself has no lock clause, and its settle tail does (`lifecycle.service.ts:658–666,434–445,506–513`). J13 starts two separate workers and waits for **both** ready signals while the row remains open and basis-free *before resuming either* (`settle-redrive.pg.spec.ts:318–351`). Afterward it requires, separately in both query traces, refused completion INSERT→rollback, subsequent gate→exactly one pending SELECT→tail lock, with no replay push/completed event, then one terminal CAS, one basis INSERT and one settle event across the workers (`settle-redrive.pg.spec.ts:215–236,352–372`). An implementation where B merely encounters A's already-terminal run fails the second readiness/trace requirement.

   The R36 diff changes only the injected-basis-failure retry premise: the **initial** failed insert still requires rollback, NULL terminal, zero basis and no settle event, while the refused-claim retry now requires one CAS, one basis and a non-NULL terminal, retaining no push (`test/rls-g2-s10c.spec.ts:226–249`; `git diff 3db615c0 45b4da1d -- test/rls-g2-s10c.spec.ts`). It does not relax the adjacent concurrent-claims or fenced cases (`rls-g2-s10c.spec.ts:203–223,251–273`). R36 alone is structural rather than a full verdict-equivalence test; J12/J14/J13 supply the stronger same-shape proof (`settle-redrive.pg.spec.ts:238–275,318–395`). No live result is claimed.

5. **First-run risk.** J13 passes `txTimeout: 60000`, but the worker substitutes that option **only** when a transaction has no explicit options; the tail explicitly uses `S9_SNAPSHOT_TX_OPTIONS.timeout = 20_000` (`settle-redrive.pg.spec.ts:327–351`; `test/utils/g2-s11-worker.cjs:204–220`; `lifecycle.service.ts:63–67,489–499`). Interleaving: worker A starts its tail transaction and pauses before the lock; worker B is still finishing its pass; if B takes >20 seconds after A's tail begins to signal ready (including the parent's open-row/basis checks), A's transaction times out before resume. This is a **C proof-flake risk**, not a fabricated terminal or demonstrated likely loss of the single proof: the fixture has five staged rows and both workers start together (`settle-redrive.pg.spec.ts:102–122,339–351`). Minimum response if observed: report the elapsed readiness times and route a narrowly scoped barrier/timeout adjustment to the harness owner before rerunning; do not weaken the two-ready requirement or change product semantics. The 90-second worker kill timer is an independent outer bound (`test/utils/g2-s11-pg-harness.ts:139–156`).
