## A1 — merged token pairs have a non-unique cursor key (blocking)

- **HARM:** `getEntities(..., 'workouts', ..., limit=1)` can permanently omit a reconstructed ledger row, or present an unstable first row, when two source tokens of the *same platform and family* have the same `source_id`. The source spec explicitly permits this fan-in: `src/scout/reconstruct/sources/s10_unseen.json` declares both `u10-routines` and `u10-sessions` as `workouts` under `sharedIdSpaces`; `src/scout/reconstruct/mapping-spec.ts:109-124,380-428` accepts that shape. The engine plans both token groups (`src/scout/scout-reconstruct.service.ts:178-194,247-264`) and writes each ledger row under its **own token** (`:445,576-594`); the ledger unique key includes `entity_type` (`prisma/schema.prisma:6978-7001`). Thus rows `(source_id=x, source_platform=s10_unseen, entity_type=u10-routines)` and `(x,s10_unseen,u10-sessions)` can coexist as separate reconstructed outcomes.
- **Mechanism:** S11-DE now selects **both** token pairs through `classifyFamilyScope` (`src/scout/scout-family-scope.ts:89-102`) but both readers still order and cursor by only `(source_id, source_platform)` (`src/scout/scout-roster.service.ts:167-175,190-202`; `src/scout/scout-entities.service.ts:193-201,215-222`; `src/scout/scout-cursor.ts:30-32,134-146`). If a page ends after the first tied row, `hasMore` is true and the emitted v2 cursor is `(x,s10_unseen)`; the next page's strict `>` predicate excludes **both** tied rows. SQL ordering between the tied rows is also not defined. The same defect applies to roster for a valid future source spec declaring two `clients` steps with a shared id space. Current new service tests merge different platforms or disjoint ids (`test/scout/roster/scout-roster.service.spec.ts:1074-1109`; `test/scout/entities/scout-entities.service.spec.ts:1547-1560`) and do not hit a same-platform/same-id cross-token tie.
- **EXACT THING BLOCKED:** landing S11-DE as a correct bounded, deterministic native reader for every data-only source spec; a coach may never see a reconstructed workout/roster ledger entry after following `next_cursor`.
- **MINIMUM CLOSURE:** make pagination's total order and continuation include the ledger's unique tie-breaker `entity_type` after `(source_id, source_platform)`, with a versioned cursor carrying that token and explicit compatibility/fail-closed handling of old pair-only cursors at ambiguous boundaries. Keep the `(coach_id,intent_id,classified pairs,status)` predicate on every boundary/page read. Add a service regression for each reader with two token pairs on **one platform and one source_id**, page size 1, asserting every ledger outcome is visited exactly once with stable order; cover legacy boundary ambiguity and any existing v2 compatibility decision.
