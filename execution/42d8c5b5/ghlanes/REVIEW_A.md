## Findings

1. **A — A partial matrix can be green as if it were full proof.** `STAGES=guard` in [preflight.sh L22, L35–49](https://github.com/BradleyGleavePortfolio/growth-project-backend/blob/4a88f3eb33f5affcc39486eccd0323a95936085f/proof/preflight.sh#L22-L49) excludes all live S11 and S10-B work. [aggregate.sh L19–38](https://github.com/BradleyGleavePortfolio/growth-project-backend/blob/4a88f3eb33f5affcc39486eccd0323a95936085f/proof/aggregate.sh#L19-L38) audits only the emitted matrix and accepts unpinned totals, including S10-B `0/0`. A local replay using the genuine 419a756d guard receipt, `STAGES=guard`, and a one-job matrix exited **0** with **VERDICT: PASS**, S11 `95/95`, S10-B `0/0` (`REVIEW_A_replay_guard/SUMMARY.md`). **Harm:** required migrations and tests can be unexecuted under a green aggregate. **Blocks:** using generic `PASS` or successful workflow conclusion as full-lane evidence. **Minimum closure:** distinguish a partial/diagnostic verdict from authoritative proof; for authoritative runs require exactly every required stage in both lanes and the optional stage whenever present at the target, and reject a zero-job lane. An external consumer must also independently require `STAGES` absent (or an enumerated full stage set) until fixed.

2. **A — An explicit per-stage expectation does not require that optional stage to run.** [preflight.sh L42–44](https://github.com/BradleyGleavePortfolio/growth-project-backend/blob/4a88f3eb33f5affcc39486eccd0323a95936085f/proof/preflight.sh#L42-L44) drops absent `journey-full`; [aggregate.sh L30, L37](https://github.com/BradleyGleavePortfolio/growth-project-backend/blob/4a88f3eb33f5affcc39486eccd0323a95936085f/proof/aggregate.sh#L30-L37) applies `EXPECT_journey-full` only inside the scheduled-job loop, then records the skip without checking the expectation. Replay of the real 54be96f1 artifacts with `EXPECT_journey-full=6`, `EXPECT_TOTAL_s11=127`, `EXPECT_TOTAL_s10b=41` still exited **0** and printed **PASS** and `SKIP_ABSENT_AT_HEAD` (`REVIEW_A_replay_optional/SUMMARY.md`). **Harm:** the operator can believe a pinned six-test stage was enforced when it did not run. **Blocks:** interpreting an `EXPECT_<stage>` pin as proof of stage presence. **Minimum closure:** reject an expectation for a skipped stage, or add an explicit required-stage manifest and fail on any absence; optionally allow a separately named, acknowledged skip policy.

3. **A — Expectation typos are silently accepted.** [preflight.sh L14–21](https://github.com/BradleyGleavePortfolio/growth-project-backend/blob/4a88f3eb33f5affcc39486eccd0323a95936085f/proof/preflight.sh#L14-L21) accepts *any* `EXPECT_*` name, while [aggregate.sh L30, L38](https://github.com/BradleyGleavePortfolio/growth-project-backend/blob/4a88f3eb33f5affcc39486eccd0323a95936085f/proof/aggregate.sh#L30-L38) looks up only known stage and lane keys. The guard-only replay with `EXPECT_guarrd=500` and `EXPECT_TOTAL_sll=500` returned **PASS**, displaying both totals as **not pinned** (`REVIEW_A_replay_guard_typo/SUMMARY.md`). **Harm:** a misspelled count pin is not enforced, especially material for guard's static lower bound of 11 versus the qualified 95 tests. **Blocks:** trusting a PROOF_TARGET containing human-supplied EXPECT keys without manual validation. **Minimum closure:** whitelist the exact stage and lane expectation keys, require nonnegative decimal values, reject duplicates and unknown keys, and report which pins were actually checked.

4. **A — Parallel isolated stages are not equivalent to the serial local lanes.** [workflow L33–74](https://github.com/BradleyGleavePortfolio/growth-project-backend/blob/4a88f3eb33f5affcc39486eccd0323a95936085f/.github/workflows/proof-lanes.yml#L33-L74) creates a separate job for each stage, and [stage.sh L107–162](https://github.com/BradleyGleavePortfolio/growth-project-backend/blob/4a88f3eb33f5affcc39486eccd0323a95936085f/proof/stage.sh#L107-L162) starts a fresh PG cluster and bootstraps it for each live job. The local `execution/42d8c5b5/proof/lane-s11.sh` and `lane-s10b.sh` each bootstrap **once**, then run their stage table in order on that same cluster (S11 approximately L188–281; S10-B approximately L183–276). **Harm:** a later test can pass against a fresh DB on GitHub but fail after an earlier stage changed the shared DB locally; the builder's assertion that this difference can only cause GH failures is not generally true. **Blocks:** claiming these parallel jobs are behaviorally identical to the local end-to-end proof for arbitrary future targets. **Minimum closure:** serialize stages within each lane against one shared cluster, while parallelizing the two lanes, or require and retain a full local serial run for every SHA used as binding proof. Existing qualification shows equality of counts for two heads only.

5. **A — The summary does not test the matrix job's GitHub conclusion.** [workflow L82–97](https://github.com/BradleyGleavePortfolio/growth-project-backend/blob/4a88f3eb33f5affcc39486eccd0323a95936085f/.github/workflows/proof-lanes.yml#L82-L97) has `needs: [preflight, stage]` and `if: always()`, but exports only `needs.preflight.result`; [aggregate.sh L14–38](https://github.com/BradleyGleavePortfolio/growth-project-backend/blob/4a88f3eb33f5affcc39486eccd0323a95936085f/proof/aggregate.sh#L14-L38) requires successful preflight and receipts, **not** `needs.stage.result == success`. A stage that produced/uploaded a passing receipt but then finished unsuccessfully can yield a **green aggregate job and green SUMMARY**. GitHub's **overall workflow** should still be red because the failed stage is itself a job: this finding concerns the aggregate's own claimed verdict, not an assertion that GitHub's overall conclusion would be success. **Harm:** a reader relying on the summary alone can overlook a failed matrix job. **Blocks:** treating the aggregate job/summary as the authoritative workflow result. **Minimum closure:** pass `needs.stage.result` to aggregate and fail unless it equals `success`; consumers must also check the overall workflow and individual job conclusions.

6. **A — The run does not pin the reviewed harness commit.** [trigger.sh L13–20](https://github.com/BradleyGleavePortfolio/growth-project-backend/blob/4a88f3eb33f5affcc39486eccd0323a95936085f/proof/trigger.sh#L13-L20) fetches and branches from the *current* mutable `proof/harness`, without asserting `4a88f3eb...`. The run workflow is taken from the pushed `proof/run/*` commit itself; [stage.sh L54–59](https://github.com/BradleyGleavePortfolio/growth-project-backend/blob/4a88f3eb33f5affcc39486eccd0323a95936085f/proof/stage.sh#L54-L59) records `HARNESS_COMMIT` as that **run** commit, and [aggregate.sh L22–38](https://github.com/BradleyGleavePortfolio/growth-project-backend/blob/4a88f3eb33f5affcc39486eccd0323a95936085f/proof/aggregate.sh#L22-L38) does not verify its parent or workflow/script hashes. Both observed qualification run commits do have parent `4a88f3eb...`, but future run branches need not. **Harm:** a modified proof/run workflow or changed harness parent could report green under different, even vacuous, rules while appearing to be this reviewed harness. **Blocks:** extrapolating this review to new runs by branch name or summary alone. **Minimum closure:** have the trusted launcher fail unless base == exact reviewed commit; verify a run commit has exactly that parent and its tree differs only by `PROOF_TARGET`, and check this binding out of band before accepting each run. Do not rely on checks implemented only by a self-modifiable workflow.

7. **B — Migration identity is count-and-max rather than exact applied-set comparison.** [stage.sh L95–96, L151–160](https://github.com/BradleyGleavePortfolio/growth-project-backend/blob/4a88f3eb33f5affcc39486eccd0323a95936085f/proof/stage.sh#L95-L160) records the target's migration **directory count and last name** and tests them against the database's finished, non-rolled-back **row count and max name**. These equalities do not prove all individual migration names occur exactly once (the local runners use this same weaker rule). **Harm:** compensating omission/duplicate rows can satisfy identity despite an incorrect applied set; no such mismatch was observed in these qualifications. **Blocks:** asserting exact migration-set identity solely from these checks. **Minimum closure:** compare sorted individual directory names to sorted applied migration names, reject duplicates and unfinished/unexpected records; retain `migrate deploy` success and per-job target binding.
