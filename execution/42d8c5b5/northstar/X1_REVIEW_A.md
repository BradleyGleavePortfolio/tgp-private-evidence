## Blocking findings

### A1 — Capture survives the run and can continue on an earlier origin

`background.js:772-776` clears the in-memory authorization and unregisters the collector, but does not stop capture sessions. `shared/capture.js:149-203` fixes `expectedOrigin` at attachment and `:167-188,233-269,315-370` continues to receive debugger events and read response bodies without consulting the *current* authorized origin. The only automatic teardown events are tab removal, debugger detach and worker suspend (`:448-467`). Thus: authorize A, invoke `start_capture` on an A tab, settle the import, start a B run, and leave A open. Its debugger remains attached and reads/retains A responses while B is the only authorized run origin. `stop_capture` can also return that older snapshot. Harm: client data crosses the run's origin/capability lifetime; a revoked or stale grant is not effective against an already-attached debugger. Blocks the grant's single-origin-per-current-run confinement. **Minimum closure:** tie every capture session to a run generation and stop/drain all its debuggers on every settlement/clear; reject events/stop snapshots for obsolete generations, and cover A→B and revoked-grant cases in tests.

### A2 — Tab navigation defeats the one-time debugger and source-token checks

`shared/capture-policy.js:42-66` checks a tab URL and permission once, then `shared/capture.js:149-203` awaits debugger attach/Network.enable. There is no navigation observer or recheck before/after attach; the handle follows the tab after it navigates to B, even if B is not granted. Although `recordRequest` filters URLs before body retrieval, the debugger is still attached to and exercises `Network.enable` on B; requests to A from a B document remain capturable. Separately, `background.js:884-909` checks the tab at `tabs.get`, then awaits dynamic registration and calls `scripting.executeScript({target:{tabId}})` and `tabs.sendMessage(tabId, ...)` without checking the live document/origin or the response sender afterward. If the tab navigates to a previously granted B during those awaits, the collector can execute in B and a B token can be accepted into the A run (`:976-996`) and sent as an A bearer. Host permissions are durable across runs, so the previous B grant is a realistic case. Harm: unauthorized debugger exercise on B and possible cross-site source-token collection/misuse. Blocks origin confinement. **Minimum closure:** bind debugger and token operations to the same document/origin throughout (including navigation/detach handling), recheck permission and document identity immediately after asynchronous operations, reject wrong-document token replies, and add deterministic navigation-race tests.

### A3 — Legacy ingest still follows off-origin redirects

`background.js:642-761` authorizes `message.url` but invokes the legacy extractor with the caller's `sourceToken`. `legacy/truecoach/net.js:57-69` calls `fetchWithTimeout` without `redirect:"error"`; a source endpoint's 30x can make the extractor issue a request to a different origin. The replay fetch explicitly sets `redirect:"error"` (`background.js:814-818`), but the legacy path does not. A cross-origin redirect will normally strip an `Authorization` header, but that is not a license to make the cross-origin request (and `credentials:"include"` is set). Harm: read path reaches an unapproved origin in a run that claims single-origin confinement. Blocks the grant's confinement rule while legacy ingest remains callable. **Minimum closure:** set `redirect:"error"` on the legacy source fetch and test cross-origin redirects using the real extractor network path.

### B1 — Existing permission is mistaken for a fresh Start authorization

The popup asks on click (`popup/popup.js:208-233,162-181`), but the worker accepts either `start_import` or `start_ingest` from *any extension page* without a gesture-bound one-run authorization handoff (`background.js:1158-1166,1218-1251`). `authorizeSourceOrigin` only asks `permissions.contains` (`:603-623`). Chrome's optional permission can remain granted after a past run, so an extension-page message can start another run against A using that stale grant, even when no current Start-request exchange occurred. Legacy `start_ingest` also accepts a caller-supplied token (`:703-707`), not a token tied to a live tab. Harm: authorization-by-possession of a durable browser permission instead of the specified Start operation; an extension-page bug/compromise can invoke a token-bearing import without a new user gesture. Blocks strict “Authorization = Start.” **Minimum closure:** make the worker consume a single-use, gesture-originated start authorization bound to tab/document/origin; retire or equivalently gate the legacy entrypoint and its token argument.

### B2 — Dynamic collector cleanup failure is silently ignored

`background.js:870-879` catches every `unregisterContentScripts` failure and logs only `source_collector_unregister_skipped`; `settleRun` then drops the guard (`:772-776`). Therefore “always unregistered” is false on a Chrome API failure: the collector registration for old A can remain active on future A loads after that run, including during a B run. `persistAcrossSessions:false` does not substitute for successful run-time unregister. Harm: retained content-script execution outside the run. **Minimum closure:** fail closed on cleanup failure, verify removal/retry safely before admitting another run, and test an unregister rejection.
