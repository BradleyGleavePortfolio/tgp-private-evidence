## 2. Findings

### F1 — Class **A** (product): fence identity literal is `search_path`-dependent; the shipped `down.sql` refuses with the fence present and `drained` is unreachable

**Fact.** `FENCE_TRIGGER_DEFINITION` (`src/scout/scout-ledger-backfill.ts:37-38`) and the identical literal in `down.sql:55-56` expect `pg_get_triggerdef(oid)` to render `… EXECUTE FUNCTION public.scout_ledger_platform_fence()`. PostgreSQL 17 `pg_get_triggerdef_worker` always schema-qualifies the **table** in non-pretty mode, but renders the **function** through `generate_function_name`, which sets `nspname = NULL` (no qualification) whenever an unqualified lookup under the session `search_path` resolves to the same function ([PostgreSQL REL_17_STABLE ruleutils.c](https://raw.githubusercontent.com/postgres/postgres/REL_17_STABLE/src/backend/utils/adt/ruleutils.c)). Under any session whose `search_path` contains `public` — psql default `"$user", public`, the CI `migration-dry-run` psql, the harness `sql()`/`sqlFile()`, and Prisma sessions (schema param `public`) — the rendered string is `… ON public."ScoutReconstructionLedger" FOR EACH ROW EXECUTE FUNCTION scout_ledger_platform_fence()` and **never equals the literal**. Nothing in the repo pins an empty `search_path` for these sessions (no `ALTER DATABASE/ROLE … search_path`; the only `search_path` pins are on S1's function bodies).

**Concrete harm / blocked decision.**
1. `down.sql` DO-block raises `G2-B fence absent` while the fence is installed → the shipped rollback of a T4 migration is unusable through its own path (G13 "prove rollback where possible"); the repo's `migration-dry-run` CI job, which applies every new directory's `down.sql` via psql and re-applies forward, would FAIL on this directory.
2. `readDrainState().fenced` is always `false` → `backfillLedgerPlatform` can never return `drained`; with the fence installed the CLI exits 4 (`complete_unfenced`). The verdict that gates R ("drained with fence present") cannot be produced, so the B stage cannot deliver its one decision; operators would be trained to treat exit 4 as success, hollowing out the fence's evidentiary value. Fail-closed direction (no false Complete), but a materially wrong product report.

**Proof coverage.** The DB-free spec cannot see it (fake returns `fences:1`). The live spec WOULD catch it at stage 3 (`installed.triggers … FENCE_TRIGGER_DEFINITION`) and stage 7 (`sqlFile(bDownFile)` throws) — so the proof is honest, but buying the PG run before the fix is wasted execution.

**Minimal closure (source-only, B files only).** Make the fence identity check `search_path`-independent in exactly the two places that consume it, without changing the trigger/function themselves: e.g. structural catalog predicate `t.tgfoid = 'public.scout_ledger_platform_fence()'::regprocedure AND t.tgtype = 7 /* ROW|BEFORE|INSERT */ AND t.tgqual IS NULL AND NOT t.tgisinternal` (plus `t.tgenabled <> 'D'` in the library), **or** evaluate `pg_get_triggerdef` under an explicit empty `search_path` (`SET LOCAL search_path = ''` after `BEGIN` in `down.sql`; the library would then need its fence read inside a transaction). Update the stage-3 spec assertion / `fence()` helper to the same property (compare to the value actually rendered under the harness session, or read it under `search_path=''`). Affected scope: `down.sql`, `scout-ledger-backfill.ts` (`FENCE_TRIGGER_DEFINITION` / `readDrainState`), `test/rls-g2-b-drain.spec.ts` stage-3 expectation, `g2-b-drain-harness.ts` `fence()` if the helper changes. Migration up (`migration.sql`) needs no change (its rerun guard is name/regprocedure-based). Execution unlocked: phase A gate + DB-free spec + the single PG run become worth buying; CI `migration-dry-run` down/up parity becomes passable.

### F2 — Class **B** (proof): stage-3 ACL assertion is false under the fixture's (and Supabase's) default privileges

**Fact.** `test/utils/g2-pg17-bootstrap.sh:124-126` sets `ALTER DEFAULT PRIVILEGES FOR ROLE postgres IN SCHEMA public GRANT ALL ON FUNCTIONS TO anon, authenticated, service_role` (mirroring Supabase). B's function is created by `postgres` via `prisma migrate deploy`, so its ACL carries explicit EXECUTE grants for those three roles; `migration.sql:83` revokes only `FROM PUBLIC`. `has_function_privilege(<role>,'public.scout_ledger_platform_fence()','EXECUTE')` therefore returns `t`, and `test/rls-g2-b-drain.spec.ts:262-268` (`.toBe('f')` for all three roles) fails for a non-product reason.

**Product effect:** none. A trigger-returning function cannot be invoked directly by any role (`trigger functions can only be called as triggers`, SQLSTATE 0A000); the migration comment "nothing is callable" is true by PostgreSQL rule, not by ACL. Handoff review-question 2 (EXECUTE checked at CREATE TRIGGER time) is correct and unaffected.

**Minimal closure (test-only):** replace the three `has_function_privilege … 'f'` expectations with the property actually protecting the boundary (direct call refused with 0A000 for each role, and/or `proacl` contains no PUBLIC `=X/` entry). Do **not** widen `REVOKE` to the API roles as a "fix" — that is a product change that buys nothing. Unlocks: stage 3 can pass on the real fixture.
