## 4. Findings (stable IDs S2-A-nn)

### S2-A-01 — Environment binding provides no human authorization at this head (material for release use; not a merge blocker)
Evidence: `fly-deploy.yml` L86–88 binds `deploy` to `environment: production`; hosted state (`evidence/backend-environments.json`) shows only `noble-celebration / production` with `protection_rules: []` and `can_admins_bypass: true`; GitHub auto-creates a referenced environment unprotected. At `b801a776` the gate performs no check on the environment, so the only human step is the dispatch itself, and any write-access identity can dispatch from `main`. The workflow header says it "relies on" hosted controls that do not exist, and the LANDING_PROPOSAL (written against `4a63b8ae`) says the gate "refuses to run unless that environment already has ≥1 required reviewer" — **false for this head**.
Consequence: a deploy at this head is exactly as authorized as its dispatcher; G07/G16 "missing switches must not silently activate" is not met for the environment control. Disposition: material for **deploy clearance**; nonmaterial for **merging the source**, because merging removes the current `push: main` auto-deploy and is strictly safer than main today. Smallest remediation: the R1.2 step-5 environment check (see §7) plus hosted step 1 of the proposal executed and read back before first dispatch.

### S2-A-02 — Gate accepts an empty/errored CodeQL analysis (nonmaterial, cheap hardening)
Reproduced: fixture analysis `{commit_sha: sha, tool.name: "CodeQL", rules_count: 0, results_count: 0, error: "extraction failed"}` → gate `PASS` (my probe, `/tmp/audA`). The gate proves an upload happened, not a non-empty scan (G07 "empty scans are not success"). Practical exposure is low because the `analyze` job must also be green. Remediation: additionally require `.error == ""` (or null) and `.rules_count > 0`; add one negative test.

### S2-A-03 — Invariant 5 overstates the gate's SBOM re-check (nonmaterial, truthful-claims)
REPORT invariant 5 says the gate "re-downloads and re-checks" the SBOM; the gate only re-checks `bomFormat` and `components > 0`. The dev-only-leak/prisma-present proof runs only inside `sbom.yml`. Acceptable design (that run is trusted evidence), but the claim should say so, or the gate should run `assert-prod-sbom.sh` against the downloaded file.

### S2-A-04 — No gated rollback route; operator runbook now stale (nonmaterial, decision + docs required before release use)
`release_sha` must equal the current `main` head, so the gated path is forward-only: rolling back means a revert commit on `main` plus a full CI/CodeQL/SBOM cycle before dispatch. `docs/deploy-runbook.md` §3 step 4 still prescribes an out-of-band `fly deploy --image registry.fly.io/<app>:<previous-tag>` (bypasses gate and `verify-fly-release.sh`), and §8.1/§8 step 3 still say "Push any commit to `main`" deploys and "fails red on every push to main". Migration coupling itself is unchanged and sound: `release.sh` aborts the deploy before machines flip. Remediation: record the forward-only decision, update runbook §3/§8, name the emergency out-of-band route explicitly as ungated.

### S2-A-05 — No migration-apply evidence bound to the release sha (nonmaterial, S1/S2 coordination)
`migration-dry-run.yml` runs only on `pull_request` with path filters, so no `migrations-apply` run exists for a main sha and it cannot be a gate input. The release relies solely on `release.sh` at deploy time. Option: add `push: [main]` to `migration-dry-run.yml` and include `migrations-apply` in `REQUIRED_WORKFLOWS`.

### S2-A-06 — Post-deploy manifest uploads raw machine config (nonmaterial)
`flyctl machines list --json` is written to `release-evidence/machines.json` and uploaded (90 days). Machine objects include `config.env` and full config. Not secrets, but internal plain configuration; filter to `{id, region, state, image_ref}` before upload.

`actions/download-artifact@v4` (new, tag-pinned; runs before `flyctl deploy`, so a failure is fail-closed) and `superfly/flyctl-actions/setup-flyctl@master` (unchanged from main; installs the binary that receives `FLY_API_TOKEN`). Pin both by sha when a network-capable step can resolve them.
