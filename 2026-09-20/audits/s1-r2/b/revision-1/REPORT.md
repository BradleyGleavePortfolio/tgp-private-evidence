## 4. New findings (stable IDs S1-R2B-NN)

### S1-R2B-01 — Timeout-leak "proof" is vacuous — NONMATERIAL (truthfulness of packet claim; source fix is correct)
- Where: harness `:118` and `:139` read `current_setting('lock_timeout')` over a fresh `psql` connection; `R1_FINDINGS_DISPOSITION.md` records this as proof of A-03.
- Why it matters: a same-connection leak (the actual A-03 mechanism — Prisma applies pending migrations on one connection) is not observed by either check. The `RESET` lines are present and correct by inspection, so the *product* is fine; the *claim* "proven by harness" is not.
- Consequence: none to customers; G09 truthfulness item for the packet. Fix is trivial: in one psql session run `\i migration.sql` then `SHOW lock_timeout; SHOW statement_timeout;` and assert `0|0` (or the role default), or apply two migrations in a single `migrate deploy` and read settings from `pg_settings`/`current_setting` inside the second. Suggest the parent runs the one-line same-session command (below) rather than blocking on it.

### S1-R2B-02 — "Whole-file rollback OBSERVED" is not what the harness observed — NONMATERIAL (precision; bounded by idempotency)
- Where: `migration.sql:51–55` ("PostgreSQL runs the multi-statement file Prisma sends as one implicit transaction, so the whole migration rolls back (OBSERVED, not assumed…)").
- What was observed (run-05 detail log lines ~1009–1030): blocker holds `DunningAttempt` (harness `:103`); the failure is `55P03` raised inside the **first** DO block at `ALTER TABLE public."DunningAttempt" ENABLE ROW LEVEL SECURITY` (`inline_code_block line 23`), i.e. the first DDL-bearing statement of the file (preceded only by two `SET`s). A DO block is one statement and always rolls back atomically on error; the "pre-state untouched" assertion is therefore satisfied whether Prisma sends the file as one implicit transaction or stops at the first failing statement. The test cannot distinguish the two, so "whole migration rolls back — OBSERVED" is not supported by it.
- Consequence: if Prisma in fact executes statement-by-statement without an implicit transaction, a mid-file failure (e.g. lock timeout in the partition loop or `CREATE OR REPLACE FUNCTION` after the 14-table block) would leave a partially applied state. That state is *safer* than the pre-state (only tightening) and the migration is idempotent, so `resolve --rolled-back` + `deploy` converges — R1-B already concluded this and I agree; no exposure or data risk. It is a G09 wording overclaim, cheap to fix: either change "OBSERVED" back to "expected" or move the blocker to a partition (`community_messages_2027_01`, protected in the *second* DO block) so the assertion actually covers cross-statement rollback (tables ENABLE'd in block 1 must be back to pre-state). The latter is a ~1-line harness change and would make the claim true.

### S1-R2B-03 — verify.sql 1b asserts an environmental precondition the migration does not establish — NONMATERIAL for S1 merge; INTEGRATION RISK for S2 release gate
- Where: `verify.sql:99–107` requires `has_table_privilege('service_role', <rel>, priv)` for all four privileges on all 18 relations. Nothing in `migration.sql` GRANTs to `service_role`; the privileges exist only because Supabase default privileges (modelled in `supabase-like-bootstrap.sql`) granted them. In CI's `_supabase_bootstrap.sql` (roles only, no default privileges) `service_role` holds no table privileges, so verify.sql would FAIL there even after a correct apply.
- Consequence today: none in CI (no workflow at this head runs verify.sql). On the integrated head, S2's `scripts/release.sh` step 4 runs every `prisma/migrations/*/verify.sql` via `prisma db execute --url DIRECT_URL` against production after `migrate deploy`. If production `service_role` ever lacks a grant on one of these relations (or a future partition created by a non-default-privilege path), the release aborts with a "service_role lost X" that is **not** an exposure and affects no known caller (the app is expected to run as `postgres`/BYPASSRLS). Operators must be able to tell that class apart from an RLS/REVOKE failure. Options (S1 lane): (a) add `GRANT SELECT, INSERT, UPDATE, DELETE ON TABLE … TO service_role` to the migration so 1b becomes a true postcondition (also makes CI-from-empty verify pass); or (b) demote 1b's missing-grant case to a NOTICE with a distinct prefix; or (c) keep as-is and document the distinction in the release runbook. (a) is my recommendation — tightening-neutral and self-establishing. Not merge-blocking.

## 5. Independent design review at 90a6647

- **DDL correctness / tightening-only.** All statements are `ENABLE`/`FORCE` RLS, `REVOKE … FROM anon, authenticated`, restrictive `deny_all_*` policies (`USING (false)`, `WITH CHECK (false)`), a permissive `service_role` ALL policy, `search_path=''` pinning with schema-qualified bodies for `community_messages_create_month_partition`, `_protect_partition`, `app.*` helpers, and `GRANT EXECUTE … TO service_role`. No policy widens any role; no data DML. Idempotent by construction (`IF NOT EXISTS`/`CREATE OR REPLACE`/`DROP … IF EXISTS` patterns; RAISE guards are intended fail-closed).
- **Cumulative chain.** Harness replays the parent chain (164) + `rls_fitness_backend.sql` to rebuild the observed pre-state, proves exposure (verify.sql fails, 241–254 problems named), then applies the candidate through real `prisma migrate deploy` (165). `replay-main-c23b9d9.log` (at 620b47fc, same migration content for DDL purposes) shows 165/165 from empty on PG 17.6 as non-superuser BYPASSRLS `postgres`. No collision with other lanes' migration names (S5 adds `20261221000000_enable_pg_stat_statements`, which sorts earlier; RESETs mean no timeout carry-over either direction).
- **Partition boundaries.** Existing partitions discovered via `pg_inherits` at apply time (4 in fixture: `2026_12`, `2027_01`, `2027_02`, `default`); future partitions covered by the `create_month_partition` wrapper calling `_protect_partition`; `verify.sql` re-derives the partition set from the catalog so any partition created outside the wrapper fails verify. Parent-path behaviour (coach/member/non-member reads, member INSERT routing to a protected partition, `app.*` with `search_path=''`) passes. Nuance: the parent `community_messages` is *not* one of the 18 and keeps its existing permissive policies — correct, since the design protects direct partition access only. No scheduler exists for partitions after `2027_02` (pre-existing, routed).
- **Timeouts / locking.** `SET lock_timeout='5s'`, `statement_timeout='60s'` at file start, RESET at end; DO block of 14 tables is a single statement holding earlier ACCESS EXCLUSIVE locks while waiting for later ones (documented worst case). Observed: direct psql `55P03` in ≤12 s and Prisma `P3018` in ≤20 s under a held lock. Under a transaction-mode pooler the RESET is what prevents contaminating a pooled server connection — good, but `DIRECT_URL` should still be a direct 5432 connection for `migrate deploy`.
- **Recovery.** `P3018` leaves `_prisma_migrations` row with `finished_at NULL, rolled_back_at NULL`; documented `resolve --rolled-back` then `deploy` converges and verify passes (observed). Reversal invariant: after `down.sql`, `migrate status` is "up to date"; `resolve --rolled-back` on clean history refuses (`P3012`, detail log 1381–1383); with an earlier failed row it prints "marked as rolled back" and changes nothing about the applied row (detail log ~1057; harness `:129–131`). Forward repair by re-applying `migration.sql` with `-1` is the correct documented path. S2 reports carrying this rule into the runbook — good, but that is S2's head, not this one.
- **Reversibility.** `down.sql` restores original function bodies (`RESET search_path`, comment cleared, `GRANT EXECUTE TO PUBLIC` approximating the original default-privilege ACL), drops policies, disables FORCE/RLS, and **re-grants ALL to anon/authenticated on the 18 relations and any later partitions** — i.e. it deliberately re-creates the exposure. Header labels it operator-only; acceptable for a gate artifact, but anyone running it live must understand it re-opens the tables.
