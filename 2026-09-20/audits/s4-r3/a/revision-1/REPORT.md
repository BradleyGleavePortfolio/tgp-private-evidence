## 2. Material findings

### S4-R3-A-01 — R3 regression: detaching a pending snapshot loses same-epoch coalescing

**Disposition: OPEN / MATERIAL, extension session owner; blocks the claimed coalescer/recovery repair and cumulative lane clearance.** The new unconditional detach in `establishSession` can remove a refresh whose token/epoch snapshot has not happened yet and will belong to the newly established session, not the old one. ([session lines 119–161](../../../../worktrees/s4-r3/shared/session.js), [R3 reproduction](coalescer-transition-r3.json))

Reproducible ordering using the actual session module, asynchronous Chrome-storage mock and synthetic fetch:

1. Begin `establishSession`; hold its `storage.session.set` while it owns the state lock.
2. Call `refreshAccessToken`; it installs `refreshInFlight` outside the lock and queues its snapshot behind the establish.
3. Release storage persistence; establish increments the epoch and detaches that slot.
4. The queued refresh snapshots the **new** refresh token and starts its request.
5. Call refresh again before the first request settles: no slot remains, so a second request presents the same new refresh token. ([executable schedule](coalescer-transition-probe.mjs))

**Measured:** R3 issues two requests carrying `NEW_SYNTHETIC_REFRESH`; two synthetic successful rotating replies yield one access-token result and one `null`, because the first rotation increments the epoch. The identical R2 schedule issues one request and both callers receive the same minted token. ([R3 result](coalescer-transition-r3.json), [R2 control](coalescer-transition-r2.json))

**Consequence:** the module's explicit invariant preventing parallel refresh-token reuse is broken, and a legitimate same-session caller can receive a false auth failure; an actual single-use/reuse-detecting backend may reject or invalidate the token family, but no live backend consequence is claimed. This probe exercises the exported session API, not a demonstration of two simultaneous browser customer actions; the worker's import single-flight does not itself prove the shared session invariant across every asynchronous caller schedule. ([session invariant, lines 48–54](../../../../worktrees/s4-r3/shared/session.js), [R3 result](coalescer-transition-r3.json), [worker callers](../../../../worktrees/s4-r3/background.js))

**Narrowest remediation:** make coalescer admission/ownership and token+epoch snapshot coherent with serialized state transitions; distinguish already-snapshotted obsolete work from pending work that will snapshot the new session. Do not hold the state lock across network I/O or restore the old stale-slot blockage. Add this pending-establish schedule, pending clear/re-establish schedules, same-epoch joins and stale-finally isolation to focused tests. The existing new tests await the old snapshot before transition, or await establish before starting refresh, so they miss this interleaving. ([new tests](../../../../worktrees/s4-r3/test/auth-body-deadline.spec.js), [coalescing tests](../../../../worktrees/s4-r3/test/refresh-coalesce.spec.js), [probe](coalescer-transition-probe.mjs))

### S4-R3-A-02 — Cumulative caller defect: an obsolete refresh clears an acknowledged replacement session

**Disposition: OPEN / MATERIAL, extension worker/session owner; blocks authentication recovery and cumulative lane clearance.** This is newly identified here but **not introduced by R3**: the same actual worker/router reproduction fails on R2 and R3. ([R3 result](stale-caller-r3.json), [R2 result](stale-caller-r2.json))

The refresh commit correctly returns `null` when its epoch is obsolete, but `makeSender` treats every null as authority to call unconditional `clearTokens()` and `onAuthLost()`; `session_established` is permitted from a trusted extension page during an active run. The second-ingest-401 cleanup likewise has no ownership check. ([session lines 215–231](../../../../worktrees/s4-r3/shared/session.js), [worker lines 168–183 and 882–896](../../../../worktrees/s4-r3/background.js))

The independent probe imports actual `background.js`, replay and session modules and uses the repository Chrome mock only at the browser boundary: establish old session, start one synthetic-client import, return ingest 401, hold refresh, acknowledge a new session through the real trusted router, then release the old refresh with a successful token pair. ([executable worker probe](stale-caller-probe.mjs))

**Measured:** the replacement responds `{ok:true}` and its new refresh token is stored; the stale successful response is correctly epoch-rejected, after which the caller removes the replacement token, makes `hasSession:false`, and emits “session expired — please sign in again” with an empty run snapshot. This demonstrates local loss of the newly acknowledged session, not stale-token resurrection, a real remote revocation, or proven cross-account data transfer. ([R3 result](stale-caller-r3.json), [R2 control](stale-caller-r2.json))

**Narrowest remediation:** preserve auth/session ownership through refresh outcomes and cleanup; distinguish stale work from failure of the still-current session, and conditionally clear under the same state serialization. Apply the ownership rule to retry-401 cleanup as well; obsolete work should stop without clearing or falsely expiring its replacement, and must not silently resume an old run under replacement credentials. Add integration regressions through `start_import` and `session_established` for stale success, rejection and timeout plus the unchanged-current-session auth-loss case. This is a local correctness repair, not a demand to build the entire later server-owned G3 workflow. ([worker](../../../../worktrees/s4-r3/background.js), [existing auth-loss tests](../../../../worktrees/s4-r3/test/start-import-hardening.spec.js), [probe](stale-caller-probe.mjs))

([probe code](auth-boundary-probe.mjs), [results](auth-boundary-probe.json))

Cancellation is **requested, not remotely confirmed**, and fire-and-forget cancellation is appropriate to keep a hung cancellation promise from pinning settlement; this is not proof of real Chrome network teardown behavior. The fallback for non-stream `response.json()` is time-bounded by the consumer but not byte-bounded; supported Chrome fetch responses with nonempty bodies use the stream path, so this is a helper/mock-contract qualification, not another demonstrated shipping blocker. ([net lines 82–156](../../../../worktrees/s4-r3/shared/net.js), [new tests](../../../../worktrees/s4-r3/test/auth-body-deadline.spec.js))

The 16-KiB fail-closed bound is a reasonable local defensive limit, not separately verified live server-token-size compatibility. Pairing's subsequent extension `sendMessage`/storage phase has no independent end-to-end deadline, so “finite authentication” must refer to the HTTP headers/body portion, not every browser IPC/storage failure mode. No real browser IPC/storage hang was demonstrated in this audit. ([pairing lines 119–140](../../../../worktrees/s4-r3/shared/pairing.js), [session establishment](../../../../worktrees/s4-r3/shared/session.js))

Access remains memory-owned, refresh remains in session storage, persistence precedes access-token publication, and stale refresh commits remain epoch-guarded; those controls are useful but insufficient when coalescer admission and the caller's destructive cleanup do not share their ownership.
