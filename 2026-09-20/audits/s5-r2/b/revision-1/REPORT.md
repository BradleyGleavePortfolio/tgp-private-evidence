- **S5-R2B-02 — S1's forward-repair precondition conflicts with E's actual forward file (packet wording; owner S1 via parent; blocks E release packet correctness, not S5).** S1 direction 1 says the forward file "must be idempotent under re-application". `migration.sql` is deliberately *not* idempotent: it raises `G2-E platform column already exists` on rerun (header: "Raw reruns must fail atomically"), which S5 stage 1 proves. S5 stage 5 proves a single forward re-apply from the dropped state, not idempotence. The packet must say: "forward repair applies only while the column is absent; re-running on an applied E fails closed and changes nothing; the catalog column check is the only truth signal". Also, `psql --single-transaction` around a file that already contains `BEGIN … COMMIT` is redundant (psql emits warnings; atomicity comes from the file itself) — harmless, but the packet should not imply the flag adds protection.
- **S5-R2B-03 — Implicit 5 s Prisma budget inside barrier tests; claim-race branch is effectively fixed (determinism caveat; nonmaterial).** Every `worker({pause:…})` test must reach `release()` within Prisma's default interactive-transaction timeout measured from the worker's `$transaction` start; the spec does not state this. A slow box turns "success holds claim…" or "T success upgrades…" into false failures where the T worker's transaction is rolled back and `reconstructRow` writes `failed` with reason `error:Prisma.P2028`. Classify such failures as infra (as S5-A-11) but the spec should say so. The claim-race test asserts invariants on both branches; the `down-refused` branch is practically unreachable on this fixture, so the assertion "T fails closed 500/P2022 with no partial row" is evidenced by the recorded `PG17_CLAIM_RACE_WORKER` line, not by an `expect`.
