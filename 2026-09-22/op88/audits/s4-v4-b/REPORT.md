## A-02 mechanism as traced (line-bound)

Session-wide TERM (launcher `141`, `signal_session` `55–60`) reaches the stub bash (leader) and the `timeout` group. Bash defers the trap until the foreground `( … exec timeout … ) 9>&-` at lib `100` returns, then runs `on_signal` (lib `74`): `STEP_ACTIVE` is set (lib `99`), so only `PENDING_SIGNAL`/`INTERRUPTED` are assigned — no `block`, no reap. Bash restores `$?`, so `local rc=$?` (lib `101`) captures the command's exit; `reap_owned` runs while still "active" (`103`); then `block "$id" "$rc"` (`115`) latches the step as primary, `block "SIGNAL_$pending" 143` (`116`) is secondary, `signal_during_step` is stamped (`111–112`). `result_exit FAILED` returns the step rc (`164`), which the launcher confirms (`160`) and classifies `TIMEOUT 124` (`179`). Predicates `73–87` match this exactly. The accepted set `{124,137,143}` (`78,83`) is tolerant of either uutils or GNU `timeout` signal-exit behaviour; no GNU-specific assumption is load-bearing. `/usr/bin/sleep` and `/usr/bin/timeout` are symlinks into `../lib/cargo/bin/coreutils/` (uutils); `flock`/`setsid` are util-linux binaries; `pgrep` is procps — by filesystem listing only.

## Material findings

### V4B-01 — HIGH (Stage 2) / launcher — TIMEOUT and INTERRUPTED are classified before the survivors check, releasing the lease with unverified survivors

Launcher `171` computes `SURVIVORS` after the post-exit TERM/KILL loops; `179` `TIMED_OUT → publish_and_exit TIMEOUT 124` and `180` `INTERRUPT → INTERRUPTED 143` run **before** `181` `SURVIVORS → hold_quarantine_lease`. On both paths the launcher exits and the kernel closes fd 9, so the lease (canonical in VALIDATION) is free while owned survivors may still exist. `hold_quarantine_lease` is reached only when the runner itself is still alive (`156–158`) or on the non-timeout, non-interrupt path (`181`). The request (`35`, "either path") and the record semantics string (`90`) claim otherwise; the record itself would be truthful (`survivors_after_kill` non-empty, `released_at_launcher_exit=true`), but the A-04 requirement — an unverified survivor must prevent slot handoff — is violated on the two paths where survivors are most likely (deadline KILL, driver cancellation). Not exercised by any control (all require `survivors_after_kill=[]`, predicates `44`). **Smallest closure:** evaluate `[[ -n $SURVIVORS ]] && hold_quarantine_lease` before `179` (keeping the TIMEOUT/INTERRUPTED label, or exit 5), and reword request `35`. Launcher byte change → V5 + manifest.

### V4B-03 — MEDIUM (Stage 2 evidence truth) / lib — EXIT_RECORD still attributes the canonical lock to the runner

lib `147` (unchanged context line in the diff) writes `"lock":{"path":…test-validation.lock,"holder_pid":num(sid),"mode":"flock -n held by runner for whole run; …}` for `kind==VALIDATION`. In V4 the runner never takes the lock (runner `67–75`); the holder is the launcher pid (`S4R6_LEASE_PID`). The runner's durable record — an input to final artifact attestations — therefore misidentifies holder and mode. CONTROL branch text is correct. **Smallest closure:** pass lease holder pid/kind into `publish_exit_record` (or read `S4R6_LEASE_PID`) and state "held by launcher pid N; runner verified inherited fd 9; step children 9>&-". Lib byte change → V5.

### V4B-04 — MATERIAL for grant text / request `53,80` — caller commands report echo's status, not the driver/launcher's

`bash -c 'cd … && bash controls/run-controls-v4.sh; echo "driver exit=$?"'` exits 0 regardless of the driver; if `cd` fails, `$?` is cd's status and is printed as "driver exit=…". Same for the Stage 2 launcher command. The repair-wave contract requires guarded raw status capture. **Smallest closure (grant text):** `bash -c 'cd /path || exit 70; bash controls/run-controls-v4.sh; rc=$?; echo "driver exit=$rc"; exit "$rc"'` (same shape for the launcher). No script change needed. The optional wrappers `timeout --foreground --kill-after=… bash -c '…'` (`56,84`) are ineffective as cancellation: with a trailing `echo`, `bash -c` forks the driver/launcher, TERM terminates only the outer shell and the child continues (self-bounded); if made effective, `--kill-after` would KILL the lease holder, contradicting A-04. Recommend no wrapper, or `timeout --foreground N bash launcher…` directly without `--kill-after`.

## Nonmaterial observations / optional hardening

- **V4B-02 driver cancellation route.** `cancel_active` (`34–43`) KILLs the launcher after 10 s while the launcher's own INTERRUPT teardown can legitimately take up to ~30 s (grace ≤6 + confirm 10 + post 8 + publish 5); a KILLed launcher releases the private lease with an unrecorded session. On `CANCELLED` the driver exits 96 at `81` **before** the leftover scan/lease check at `86–89`, so the log claim at `42` ("reported by the leftover scan") is untrue. Only trips when the launcher exceeds its own worst case; private lease only. Optional: run the scan/lease check before `exit 96`; lengthen grace to the launcher's post-deadline constant.
- **V4B-05 quarantine holder unverified.** `hold_quarantine_lease` (`147–155`) records `$!` of `setsid sleep infinity` without `kill -0`/`readlink /proc/$pid/fd/9` confirmation. If the holder died at once (e.g. unsupported argument), the record would falsely claim `released_at_launcher_exit=false`. uutils `sleep` is expected to accept `infinity` (Rust f64 parse), not verified in-packet. Optional: verify and record `quarantine_holder_verified`; record holder start time/cmdline so the parent's later `kill` is identity-checked.
- **V4B-06 control 5 does not discriminate the holder.** `flock -n path true` from a fresh open conflicts with the same open-file description whether launcher or stub holds it (stub inherits fd 9, `21`).
