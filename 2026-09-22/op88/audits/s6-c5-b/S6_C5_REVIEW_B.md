## 6. Proposed test-only fix: `await queryClient.cancelQueries()` + unmount-before-clear

Question: can it prevent or remove already-orphaned Queries created by `signOut` inside a case while preserving in-flight/mounted preconditions and all six assertions?

- Hook-boundary orphans (4812, 6146, 6800): **source-plausibly yes.** `cancelQueries()` (pinned `queryClient.ts`: `findAll().map(q => q.cancel({revert:true}))`, `Promise.all(...).then(noop).catch(noop)`) rejects each pending retryer; `fetch()`'s `finally → scheduleGc()` runs in the first reaction on that promise, several microtasks before the `await` in the hook resumes, arming a gc timer on a Query still in the cache; the following `clear()` → `destroy()` → `clearGcTimeout()` removes it and `cancel({silent})` is a no-op on the resolved retryer. Preconditions untouched (hooks only). Ordering caveat L-3.
- In-case `signOut` orphans (6020, 6564): **no.** They are created mid-case by `authActions.ts:352`; by `afterEach` they are already out of the cache, so `cancelQueries/removeQueries/clear/unmount` cannot see them (all iterate the cache map). "Unmount before clear" is already the `afterEach` order (`cleanup()` L138 precedes L140) and does not apply to the in-case `clear()`; the R re-arm is not the root cause — without the `recommit` re-render Q1/Q3 would still hold their F timers. Preventing them test-side requires either cancelling the in-flight `me` fetch or unmounting `MeProbe` before `signOut()`, which removes exactly the in-flight/mounted precondition the brief requires preserved; intercepting timers via `timeoutManager.setTimeoutProvider` or `unref` is a scoped variant of clear-all-timers (masking, excluded); `gcTime` changes and `--forceExit` are excluded. The only non-masking route to remove them is the product side (`signOut` settling in-flight fetches before `clear()`), which is out of this lane's scope and is not proposed here.
- Expected outcome if the proposal were run as written: C still `budget-TERM` with exactly 2 live 600000 ms timers, both `Query.removeObserver` stacks, created at the T3/T4 `recommit` instants. The receipt §4's expected "C exits on its own, 0 live 600000 timers" is **not established** and, on this analysis, predicted false.
- Upstream: official docs describe `Query.destroy` as clearing the gc timeout and silently cancelling in-flight fetches without mentioning the post-cancel re-arm ([TanStack Query reference](https://tanstack.com/query/latest/docs/framework/react/reference/classes/Query)); their generic Jest advice is `gcTime: Infinity` ([TanStack testing guide](https://tanstack.com/query/latest/docs/framework/react/guides/testing)), a blanket approach excluded by contract. Whether a newer query-core changes `destroy()` was not verified.
