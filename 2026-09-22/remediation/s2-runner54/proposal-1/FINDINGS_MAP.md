## Ownership boundary reached (K9) — smallest design, NOT implemented
An escaped descendant that calls `setsid` **and** carries an unmatched cmdline (e.g. plain `sleep`, or a future consumer binary) is outside both retained groups and anchored patterns; v5.4 will stamp `reap=ok` while it lives. K9 makes this visible as a predicted, labelled boundary (not a pass). Closing it needs an OS-level boundary. Probe (read-only, `unshare -Urpf --kill-child true` → rc 0): unprivileged user+pid namespaces are available here. Smallest design: launch each step as `setsid unshare -Urpf --kill-child --mount-proc timeout --foreground <bound> <cmd>`, so the step's whole tree dies with the namespace init and `pgrep`/`/proc` inside the step see only owned processes. **Blocking caveat**: with `-r` the step runs as uid 0 inside the namespace and PostgreSQL binaries (`initdb`, `postgres`, and the fixture's `pg_ctl`) refuse to run as root; without `-r` the uid is unmapped (overflow uid) and file access breaks. Therefore the boundary would apply to steps 10/20/21/40/45 (guard spec, refusals, harness, discriminator — node/psql clients, uid 0 inside is tolerated) but **not** to the fixture steps 30/31/32/50, and the harness's own `psql`/`node` consumers would need a compatibility check under the namespace. This is a design decision for the parent/reviewers; not made here.
